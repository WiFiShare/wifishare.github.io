Apps

Neither app is released. There is nothing to install. There is no store listing, no beta, no test build and no waiting list. The Android app is phase P2 and the iOS app is phase P3, both after the data pipeline and API. If you find a "WiFiShare" app in a store today, it is not this project's.

Two apps are planned, and they will not be able to do the same things. That is not a roadmap gap. It is a platform rule, and it is worth understanding before you expect feature parity.

Android

The Android app is the one that can collect. It scans, applies the filter rules on the device, and sends what survives in an encrypted batch. It also reads the published data, shows what is nearby and joins a network on request.

Contributing is off until you turn it on. Finding and joining networks works whether or not you ever do.

The filter runs before anything is stored, so the networks it must not collect never exist on your phone either: hidden networks, names ending in _nomap or _optout, phone hotspots, and every password-protected network. There are no accounts, no device identifiers and no advertising identifiers.

The repository is WiFiShare/android. It currently holds a README and a licence: the code has not been written.

iOS

The iOS app finds networks and joins them. It cannot scan, and it never will.

iOS does not allow apps to scan for Wi-Fi networks This is a platform rule, not a decision this project made and not something an entitlement unlocks. Apple states it in TN3111: iOS Wi-Fi API overview. Any app that claims to list the Wi-Fi networks around you on an iPhone is doing something else.

Everything about the app's scope follows from that:

Finding networks means reading the data, not looking at the air.
The app knows what is nearby because the published dump says so. It fetches the area files for the cells around you and shows what is in them.
Joining uses the system's own mechanism.
NEHotspotConfigurationManager, which shows the system prompt before joining. The app cannot join silently and does not try to.
Sharing is limited to the network you are on.
Read with NEHotspotNetwork.fetchCurrent. One network at a time, the one you are already connected to. There is no walk-and-collect mode on iOS and there cannot be. In the data, an observation from iOS can only ever be marked as coming from a connection, never from a scan.

If you have used the Android app, that is the difference to expect: on Android the app can walk and collect, on iOS it can only contribute the network you are already connected to.

Requirements and entitlements

Minimum iOS 17, because the app uses HPKE from CryptoKit, which requires it. That is the only reason, and if the crypto design in the specification changes, the minimum should be revisited rather than kept out of habit.

The two entitlements, and what each is for
EntitlementWhy
Access Wi-Fi Information To read the current network with NEHotspotNetwork.fetchCurrent, which is what sharing is built on.
Hotspot Configuration To join a network with NEHotspotConfigurationManager.

Neither grants scanning. Nothing does.

The repository is WiFiShare/ios. It currently holds the plan and a licence: the code has not been written.

What both apps will do about precision

A community-found network is known to about 150 m, so an app must not draw it as a pin on a building. Showing it honestly — as an area, with the precision stated — is a requirement in both apps, not a nicety. The same goes for this site's map.

Helping

Both repositories are open and both are at the stage where the useful work is the part that does not depend on the API being finished: a project skeleton, a geohash implementation, a client that reads area files, an offline cache, the join and share flows, and accessibility and localisation from the start rather than retrofitted. Open an issue in the repository before starting something substantial. See how to contribute.
