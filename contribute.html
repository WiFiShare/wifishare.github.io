Contribute

The project is at the stage where most of the open work is specification, scaffolding and review rather than features. That is a good stage to arrive at: the decisions that are expensive to change later are being made now.

Where the work is

Issues live in the repository they affect, not in a central tracker. Start there. For anything that crosses repositories, open the issue on spec, because the specification is what the others agree on.

What each repository is, and what it needs now
Repository What it holds What it needs
spec Data model, JSON Schemas, OpenAPI, privacy rules R1–R12 and P1–P8, test fixtures Review, mostly. Holes in the hotspot name patterns, rules that are ambiguous when you try to implement them, and fixtures for cases nobody has thought of. A missed pattern costs somebody's privacy.
api Django backend: ingest, area lookups, dump export Everything. This is phase P1 and it blocks the apps. Ingest with HPKE decryption, server-side re-checking of the filter rules, the aggregation job, the claim flow, and the weekly export.
android Kotlin app that scans, shares and joins A project skeleton, the on-device filter tested against the fixtures, a geohash implementation, a client for area files, an offline cache, and the scan and share flows.
ios Swift app that finds and joins A project skeleton with the two entitlements declared, a geohash implementation, a data client, an offline cache, the join flow around the system prompt, the share flow for the current network, and an honest presentation of precision.
data The weekly public dump Nothing to publish yet. Problems in published data, once there is any, go here as a Network problem issue.
wifishare.github.io This website Corrections, accessibility problems, translations, and anything here that overstates what exists.

If what you want to do is not covered by an issue, open one in that repository first and say what you intend. It avoids two people building the same thing in different directions, which is easy while the data model is still moving.

Privacy-filter changes need spec fixtures

A rule without a fixture is not a rule. A change to filter behaviour in any repository must come with test fixtures in spec that demonstrate the new behaviour, and the implementation must be tested against them. A pull request that changes any of this without fixtures will be asked for them before review.

This applies to, among other things:

  • the _nomap and _optout endings, which are never collected;
  • whether a network is collected at all, including password-protected networks, which are excluded unless their owner shares them deliberately;
  • the precision of a published position, and which networks get an exact one;
  • whether a hardware address is published;
  • the mobile-network rule, which excludes networks seen more than 1 km apart.

The reason is plain: a privacy rule that exists only in prose gets broken by the next refactor, and a broken filter publishes something about somebody. The fixtures are the acceptance test. A client that drops a network the fixtures keep is merely less useful; a client that keeps a network the fixtures drop is a privacy bug and must not ship.

Two things implementations must not get creative about: evaluate the age rule against the now field in the fixture file rather than the wall clock, or the suite rots; and apply the drop rules in numeric order, reporting the first that matches, because several rules often apply to the same network and the fixtures pin which one is reported.

Changing the specification

  1. Open an issue describing the behaviour change.
  2. Change the rule text and the fixtures in the same pull request.
  3. Update the changelog. A wire format that breaks a released client gets a new schema id, such as wifishare.batch/2, never a silent change to an existing one.

Pull requests

  • One logical change per pull request. A refactor and a behaviour change in the same diff are hard to review and harder to revert.
  • Commit messages in the imperative mood, with a short subject and a body that says why. The diff already says what.
  • Reference the issue the pull request closes, and keep the template filled in.
  • Say whether the change affects what is collected or what is published. If it does, link the fixtures.
  • Run that repository's tests and linters first. The commands are in its README.
  • Expect review comments on anything touching the data model, the filter or a platform permission. Those are the parts that are expensive to change later.

Licensing of contributions

There is no contributor licence agreement, the DCO is not required, and no sign-off is needed on commits. By opening a pull request you agree your contribution is licensed under the licence of the repository it lands in: AGPL-3.0 for the backend, MPL-2.0 for the apps, Apache-2.0 for the specification, ODbL-1.0 for the data, and MIT for code with CC-BY-4.0 for text on this website.

Do not contribute code or data you do not have the right to relicense that way. In particular, do not import network data from another database whose terms do not allow it.

Working on this website

It is hand-written HTML, one CSS file and two small JavaScript modules. There is no build step, no framework and no dependency to install:

git clone https://github.com/WiFiShare/wifishare.github.io.git
cd wifishare.github.io
python3 -m http.server 8000

Things worth keeping when you change it: every page except the map works with JavaScript disabled; no cookies, no analytics and no third-party embeds; no web fonts; and no claim that something exists when it does not.

Code of conduct

The project uses the Contributor Covenant, version 2.1. The full text is in the organisation's CODE_OF_CONDUCT.md and it applies in every community space, and when someone is representing the project in public.

In short: be empathetic and respectful, accept feedback gracefully, take responsibility when you get something wrong, and focus on what is best for the community. Harassment, insults, personal or political attacks, and publishing anyone's private information without their permission are not tolerated. Reports go to the organisation owners through GitHub private vulnerability reporting, or by opening an issue if the matter is not sensitive. Reporters' privacy is respected.

Reporting a vulnerability

Not in a pull request and not in a public issue. Use GitHub private vulnerability reporting on the affected repository, or on spec if you are not sure which one it is. The security policy has the scope.

A failure of the three privacy rules is a vulnerability, not a feature request: a way to make the system collect a network ending in _nomap, to collect a private network its owner has not shared, to publish a community-found network's hardware address or a finer position than its cell, or to link observations back to a person. There is no bug bounty, no funding and no swag. What you get is a reply, credit in the advisory if you want it, and a fix.

A problem with one specific Wi-Fi network's privacy is not a vulnerability report. That is the opt-out path.
