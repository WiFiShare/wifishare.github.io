How it works

From a phone that sees a network to a file anyone can download. Five steps, and a long list of things that never make it past the first one.

Described in the present tense, built in the future tense This page describes the design that the specification fixes. None of it is running yet: no app has been released, the API is not live and the dump is empty.

1. The app filters on the device

The filter runs on the phone, before anything is stored or queued. An observation that a rule drops never reaches the network at all. The server runs the same rules again when a batch arrives and rejects the whole batch if any observation breaks one, because an old app cannot be trusted to have the current rules.

What survives is one sighting of one network: the name, the hardware address, whether it is open, whether a captive portal was met, where the phone was, how accurate that position was, the signal strength, the hour it was seen, and whether the phone was scanning or connected. That is the whole record.

What is never collected

Drop rules, from privacy/filter-rules.md in the specification
Rule Dropped Why
R1 Hidden networks, and any network with an empty or missing name A hidden network is not offering itself to anyone.
R2 Names ending in _nomap or _optout The owner used the standard opt-out. Only the ending counts: a network called Bar Nomap is not opted out.
R3 Locally administered hardware addresses Phone hotspots and randomised addresses live there, and they follow a person around.
R4 Names that match the personal-hotspot patterns, such as Anna's iPhone or AndroidAP A hotspot named after its owner is personal data, and it is not a place.
R5 Anything that is not open or OWE: every password-protected network A private network enters the database only through its owner, never through a scan.
R6 Observations with no position fix, or a fix worse than 50 m A position we cannot trust would blur the wrong block.
R7 Observations more than 7 days old in the queue Stale data is not worth the privacy cost of sending it.
R8 Any observation carrying a field the schema does not define Belt and braces against a future contributor adding a device identifier.

The hotspot name patterns are anchored on purpose. An unanchored match on iphone would also drop a shop called iPhone Repair Shop WiFi, which is a place and not a person. The specification says plainly that the patterns will never be complete: they are a floor, not a claim of safety.

Three more things never go in a batch, and the specification does not give them a rule number because they are not negotiable: no device identifier, model, operating-system build, IP address, account, advertising identifier, installation identifier or list of saved networks. The only thing the app says about itself is its platform and its major and minor version, so the server can refuse a version with a known filter bug.

What is tidied up before sending

  • Hardware addresses are written in one form, lowercase with colons (R9).
  • Latitude and longitude are rounded to 4 decimal places, about 11 m (R10).
  • The time is truncated to the hour, in UTC (R11).

2. The batch is encrypted before it leaves the phone

Up to 200 observations go into one batch. Within a batch only one observation is kept per network, rounded position and hour: the one with the strongest signal. The order is shuffled. The batch carries no identifier, no sequence number, no session and no timestamp of its own, so two batches from one phone cannot be tied together (R12).

The batch is then sealed with HPKE (RFC 9180) to a public key the app ships with and refreshes from the API. Encryption happens before the request, not only in transit, so proxies, content delivery networks and access logs never see a batch in the clear — only the server holding the private key can open it.

3. The server checks it again

The encrypted batch is posted to POST /v1/batches. There is no account and no token. The server decrypts it, validates every observation against the filter rules a second time, and rejects the whole batch if one of them fails. The reply says how many observations were kept and which rules refused, and never which network.

The only thing attached to the request is a rate-limit bucket: a hash of the IP address under a salt that rotates daily. Those hashes are deleted within 24 hours.

4. Aggregation decides what may be published

A scheduled job turns observations into published networks. It applies the publish rules in a fixed order and stops at the first that refuses:

opt-out (P5) -> mobile check (P4) -> threshold (P1) -> precision (P2/P3) -> write
Publish rules, from privacy/publish-rules.md
RuleWhat it does
P5 A network on the opt-out list is never published. The list holds no addresses in the clear: each one is stored as an HMAC-SHA256 under a key only the server has, so a network can be blocked without being kept.
P4 A network seen more than 1 km apart is marked mobile and excluded entirely, not published at a coarser precision. A moving access point is a vehicle, a travel router or a phone, and publishing it would track its owner.
P1 A community-found network is published only after at least 3 observations, from at least 3 distinct rate-limit buckets, on at least 2 distinct UTC days. One person walking past three times is not a confirmation, and a new network therefore takes at least two days to appear.
P2 A community-found network is published as its name, security type, captive-portal flag, the centre of its geohash-7 cell, the first and last day it was seen, and the report counts. Never its hardware address.
P3 An owner-verified network is published at full precision, 5 decimal places, with its hardware addresses, the venue name, and the password only if the owner marked it public.
P6 A network is unpublished when it has not been seen for 12 months, when it reaches 3 reports saying it is private or gone, or when its owner withdraws it.
P7 Raw observations are deleted within 7 days of the aggregation that consumed them. Rate-limit hashes are deleted within 24 hours. A scheduled job does it, not a person remembering to.
P8 A published network's identifier is random, with no derivation from its hardware address, name or position, and is not reused.

Why a community-found network is a cell, not a pin

A network that nobody has claimed is published as the centre of its geohash-7 cell. At the latitude of Bologna that cell is about 153 m tall and 109 m wide; the specification quotes it as about 150 m, which is the taller side. The hardware address is withheld.

What a reader learns is that free Wi-Fi exists on roughly this block, which is what a person looking for Wi-Fi needs. What they do not learn is which flat a router sits in. Two consequences follow, and they are worth saying out loud:

  • The dump cannot be used to look up where a specific access point is. Community-found hardware addresses never appear in it, and the API has no lookup by hardware address.
  • The coordinate in a community record is not a measurement. It is a cell centre. Anything built on this data should read precision_m and cell rather than treating the point as a position.

An owner-verified network is the opposite case, and deliberately so: the owner asked to be found, so the position is published exactly, to 5 decimal places, carrying a stated precision of 10 m, together with the hardware addresses. That is a choice the venue makes, and the claim flow has to say so in those words before the owner confirms. See the page for venues.

5. Publication: the API and a weekly dump

Published networks are split into area files, one per geohash-5 cell, about 4.9 km across. The same document is served two ways, so a client needs one parser:

  • GET /v1/areas/{geohash5} from the API.
  • areas/<gh2>/<gh3>/<gh5>.geojson in the data repository on GitHub, committed weekly by a bot, with a monthly snapshot released for anyone who needs a stable version to cite.

Asking for an area tells the server only which 4.9 km cell the caller cares about, which is coarse enough that the request is not a position report. Clients fetch their own cell plus the eight neighbours, so a network just across a boundary is still found.

The history of the data repository is squashed once a month, on purpose. A removed network must not stay readable in an old commit forever. If someone renames their network to _nomap, or asks for it to be taken out, the removal has to be real.

The developers page has the worked path example and the licence terms.

Reading this for yourself

Everything above is a summary. The normative text is in the spec repository, and if this page and that repository disagree, that repository is right. The rules also ship as test fixtures: a client that keeps a network the fixtures drop is a privacy bug and must not ship.
